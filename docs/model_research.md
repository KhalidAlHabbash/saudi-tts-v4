# Arabic TTS model research for Apple Silicon fine-tuning

Research date: 2026-09-11  
Target: Apple M2 Max, 32 GB unified memory, macOS, local-only training, MPS/Metal preferred with CPU fallback, no CUDA dependency.  
Scope: models with downloadable checkpoints and actual training/fine-tuning code. Inference-only models do not qualify.

## Executive decision

**PRIMARY — SILMA TTS v1 (150M F5-TTS Small).** This is the best balance of Arabic quality potential, real voice-cloning conditioning, permissive weights, and local trainability. It is a 24 kHz Arabic/English flow-matching DiT trained from scratch on tens of thousands of hours, with an explicit fine-tuning recipe, matching checkpoint/config/vocabulary, and a pinned upstream trainer. F5-TTS uses Hugging Face Accelerate, whose supported single-device MPS path is selected automatically on Apple Silicon. The audited configuration uses ordinary PyTorch attention and full AdamW; `bitsandbytes` is both optional and excluded from installation on ARM64 Darwin. A conservative M2 Max launch should use batch size 1, gradient accumulation, FP32 first, activation checkpointing if needed, zero workers initially, no sample logging, and CPU fallback for unsupported MPS operations.

**BACKUP — OHF Piper (`piper1-gpl`) VITS, warm-started from a medium checkpoint.** Piper is much smaller (the Arabic ONNX is 63.2 MB, approximately 16M FP32 inference parameters) and has a current, official Lightning training pipeline, single- and multi-speaker support, Arabic eSpeak phonemization, full-checkpoint and vocoder-only warm starts, and no required CUDA package/kernel. It is the safest way to obtain a compact deployable voice if SILMA training is unstable on MPS. Its ceiling for prosody, voice similarity, and zero-shot cloning is lower, and its training source is GPL-3.0-or-later.

Do **not** make XTTS-v2 the primary on this Mac: its quality and Arabic/voice-cloning support are strong, but official training covers only the GPT encoder, its approximately 467M-parameter system is substantially heavier, MPS failures are documented, and the CPML limits the model and outputs to non-commercial use. Do **not** base the project on MMS-TTS Arabic: the checkpoint is real, but an official fine-tuning recipe is absent and upstream Fairseq explicitly assumes NVIDIA GPU/NCCL for training.

## Candidate details and source audit

### 1. SILMA TTS v1 — primary

- **Authoritative sources and pinned revisions:** [SILMA source at `96ec4bee`](https://github.com/SILMA-AI/silma-tts/tree/96ec4beedb0766fcbddbf8b49b696c4049574ed6); [SILMA Hugging Face model at `ac81834c`](https://huggingface.co/silma-ai/silma-tts/tree/ac81834c5ce305504fe4c7602187042fdd6913db); [patched fine-tuning script](https://huggingface.co/silma-ai/silma-tts/blob/ac81834c5ce305504fe4c7602187042fdd6913db/finetune_cli.py); [matching config](https://huggingface.co/silma-ai/silma-tts/blob/ac81834c5ce305504fe4c7602187042fdd6913db/config.yaml); [F5-TTS 1.1.7 source at `c96c3aee`](https://github.com/SWivid/F5-TTS/tree/c96c3aeed84f5e02aa54dc42c1193537ead39837).
- **Architecture:** F5-TTS’s non-autoregressive conditional flow-matching acoustic model. SILMA’s patch uses an 18-block DiT (`dim=768`, 12 heads, FF multiplier 2, four text convolution layers), 100-bin mel spectrograms, and Vocos. The source config chooses `attn_backend: torch`; FlashAttention is not selected.
- **Arabic frontend:** character tokenizer with supplied vocabulary, Arabic/English code switching, tashkeel support, CATT automatic diacritization, and NeMo text normalization. This is more suitable for Saudi-domain adaptation than a generic multilingual tokenizer, but the public description does not disclose the Arabic/English hour split, dialect composition, speaker count, or corpus list. Claims are therefore vendor claims rather than independently reproduced Arabic benchmarks.
- **Saudi fit:** the open v1 checkpoint is advertised for MSA/Fusha, not Saudi/Najdi/Hijazi. SILMA advertises Saudi Najdi only for its separate proprietary products. The open model is therefore a strong initialization, not an already-Saudi voice; dialect coverage must come from the project dataset and evaluation set.
- **Speaker conditioning:** prompt audio is concatenated/conditioned in the F5 objective, giving instant voice cloning and many-speaker capability without a fixed speaker embedding table. Fine-tuning should use consented target-speaker clips; it is not a speaker-embedding-only adapter.
- **Fine-tuning scope:** official SILMA instructions explicitly reuse F5-TTS 1.1.7 and replace its base config, vocabulary, and CLI with supplied files. The trainer optimizes the entire CFM/DiT and maintains an EMA model; the Vocos vocoder is pretrained/fixed. There is no official LoRA, adapter, layer-freezing recipe, or 8-bit route for Apple Silicon.
- **CUDA/dependency audit:** the F5 trainer uses `Accelerator(...)` and ordinary AdamW. F5’s package marker excludes `bitsandbytes` when `platform_machine == 'arm64'` and `platform_system == 'Darwin'`. FlashAttention is optional and guarded; the SILMA config requests PyTorch attention. NVIDIA Triton/TensorRT files are a separate deployment subtree and are not imported by the normal trainer. CUDA references in eval, Gradio monitoring, seed helpers, and optimized runtime are not part of the core CLI training computation. No required CUDA custom extension was found.
- **Apple path:** Accelerate officially enables MPS by default on Apple Silicon and supports only one MPS device (no NCCL/Gloo distributed mode). Begin with `accelerate launch --mixed_precision=no`, one process, batch 1, short clips, and `PYTORCH_ENABLE_MPS_FALLBACK=1`; only consider FP16 after loss/audio parity. The default SILMA file has 16 workers, sample logging, 100 retained checkpoints, and activation checkpointing off; all are poor first-run settings for a 32 GB Mac and should be changed before a real run.
- **Stability caveats:** SILMA v1 is new (2026), says it cannot actively support the repo, and has no published Arabic MOS/WER table. Its README contains a likely typo: `echo /path/config.yaml > .../F5TTS_v1_Base.yaml` writes a path string, while the prose says to replace/copy the config. Use the downloaded patched CLI directly and copy the actual YAML content. The Gradio launcher has an open command-injection report; use the CLI with trusted local paths, not a network-exposed Gradio instance.
- **License:** SILMA README declares MIT code and Apache-2.0 weights; the Hugging Face repository is tagged Apache-2.0. F5 upstream code is MIT. Proprietary data participated in pretraining, but that does not by itself change the published weights license.

### 2. OHF Piper — backup

- **Authoritative sources and revision:** [Piper source at `404aefed`](https://github.com/OHF-Voice/piper1-gpl/tree/404aefedbd74baa0bd43e451bc407a2b3aace0f5); [official training guide](https://github.com/OHF-Voice/piper1-gpl/blob/404aefedbd74baa0bd43e451bc407a2b3aace0f5/docs/TRAINING.md); [Arabic Kareem medium config](https://huggingface.co/rhasspy/piper-voices/blob/main/ar/ar_JO/kareem/medium/ar_JO-kareem-medium.onnx.json); [voice model card](https://huggingface.co/rhasspy/piper-voices/blob/main/ar/ar_JO/kareem/medium/MODEL_CARD).
- **Architecture/quality:** compact VITS with stochastic duration prediction, flow/posterior components, and an integrated neural vocoder. The official Arabic voice is labelled “medium,” 22,050 Hz, one speaker, and was fine-tuned from the US English Lessac medium voice. It is good for fast, deterministic local speech, but is less expressive and less faithful for voice cloning than flow-matching or XTTS.
- **Arabic frontend:** eSpeak-NG Arabic (`voice: ar`) produces IPA-like phonemes mapped into 256 symbols. Custom Unicode phonemes or exact phoneme IDs are supported. For Saudi Arabic, pronunciation quality will depend heavily on normalization, diacritics/G2P, and dialect-specific recordings; the Jordanian warm start is useful but not dialect-matched.
- **Training:** real `python -m piper.train fit` pipeline using PyTorch Lightning. It supports single/multi-speaker CSVs; a strict full checkpoint, non-strict full warm start, or vocoder-only warm start; generator/discriminator training; and ONNX export. This is full/warm-start fine-tuning, not an adapter method.
- **CUDA/dependency audit:** training dependencies are standard PyTorch, Lightning, librosa, ONNX, and a Cython monotonic-alignment extension compiled for the host. No bitsandbytes, FlashAttention, NCCL, Triton, or CUDA custom kernel is required. One unused helper contains `.cuda(non_blocking=True)`; no callers were found. The CLI touches CUDA/cuDNN backend flags, but the model tensors follow Lightning’s device. A Mac training issue about open file limits exists, so set `num_workers=0` or a small value initially.
- **Memory/feasibility:** likely comfortably within 32 GB even in FP32 with batch 1–8. MPS operation compatibility must still be smoke-tested, particularly STFT and GAN backward passes. CPU is a genuine fallback because the model is small, though convergence can take days. Official docs report training on Threadripper + NVIDIA GPUs and community success at 8 GB VRAM/alternative GPUs, not Apple benchmarks.
- **License:** current code is GPL-3.0-or-later. Piper warns that individual voices can carry different terms. The Kareem card identifies its dataset but says only “License: See URL”; verify the dataset and exact Lightning warm-start checkpoint terms before redistribution or commercial use. The ONNX hub’s repository-level MIT tag is not a substitute for a clear per-voice provenance review.

### 3. Coqui XTTS-v2 — high-quality but unsuitable primary

- **Sources/revision:** [Coqui TTS at `dbf1a08a`](https://github.com/coqui-ai/TTS/tree/dbf1a08a0d4e47fdad6172e433eeb34bc6b13b4e); [official XTTS documentation](https://github.com/coqui-ai/TTS/blob/dbf1a08a0d4e47fdad6172e433eeb34bc6b13b4e/docs/source/models/xtts.md); [GPT fine-tuning recipe](https://github.com/coqui-ai/TTS/blob/dbf1a08a0d4e47fdad6172e433eeb34bc6b13b4e/recipes/ljspeech/xtts_v2/train_gpt_xtts.py); [XTTS paper](https://arxiv.org/abs/2406.04904); [CPML text](https://huggingface.co/coqui/XTTS-v2/blob/main/LICENSE.txt).
- **Architecture and support:** Tortoise-derived GPT predicts DVAE audio codes, then a customized HiFi-GAN decodes them. Multilingual BPE/text tokens, language conditioning, and reference-audio speaker conditioning cover Arabic and 15 other official languages. Output is 24 kHz. The roughly 467M parameter total is a literature estimate, not stated in the official model card.
- **Fine-tuning boundary:** the docs explicitly say the implementation “only supports inference and GPT encoder training.” The recipe loads fixed DVAE/mel statistics and XTTS checkpoint and trains the GPT trainer. There is no official end-to-end recipe for DVAE, decoder/HiFi-GAN, or all three stages; an upstream request for all-stage recipes was closed `wontfix`. It therefore offers partial, not full, adaptation.
- **CUDA/MPS audit:** single-device training can avoid distributed code, FlashAttention defaults off, and DeepSpeed can be disabled. However the broader stack has numerous `.cuda()` calls, CUDA device checks, and a CUDA-only distributed helper. MPS inference issues include hangs, missing attention masks, and a convolution channel limit; CPU fallback can work but weakens the point of the M2 Max GPU. The official recipe’s batch 3 × accumulation 84 and 30-layer, width-1024 GPT are a poor local baseline.
- **License/stability:** code is MPL-2.0, but checkpoint and outputs are CPML 1.0.0, which explicitly allows only non-commercial use. Coqui’s original company shutdown and dependency/version churn add maintenance risk even though community forks remain active.

### 4. `tts-arabic-pytorch` FastPitch — useful benchmark, not production base

- **Sources/revision:** [source at `2d18e171`](https://github.com/nipponjo/tts-arabic-pytorch/tree/2d18e171209a77189760ee1eac36382cb26ca6f2); [README/training directions](https://github.com/nipponjo/tts-arabic-pytorch/blob/2d18e171209a77189760ee1eac36382cb26ca6f2/README.md); [2025 paper](https://arxiv.org/abs/2512.00937).
- **Architecture/Arabic:** FastPitch is a parallel Transformer text-to-mel model with explicit duration and pitch prediction; a separate HiFi-GAN renders 22.05 kHz audio. Arabic text is phonetized/transliterated into a small Buckwalter-derived inventory; Shakkala/Shakkelha can add diacritics. The base is single speaker; experimental multi-speaker weights use synthetic XTTS voices plus Tunisian MSA.
- **Fine-tuning:** checkpoints, configs, preprocessing, standard and adversarial training scripts, and resume state are present. There is no polished `--finetune` recipe or parameter-efficient path, but setting a restore checkpoint and continuing full training is straightforward. The README’s default `configs/nawar.yaml` is absent at the audited revision; use a real FastPitch config only after reconciling paths/options.
- **CUDA/MPS audit:** no CUDA-only third-party dependency or compiled CUDA kernel was found. Standard scripts choose CUDA if available, otherwise CPU, and never select MPS. Adversarial scripts allocate random tensors with hard `.cuda()`, audio preprocessing hardcodes `device='cuda'`, and alignment code calls CUDA-specific tensor device APIs. CPU is usable; MPS requires a focused portability patch and tests. The approximately 60M acoustic+vocoder parameter size is otherwise easy for 32 GB.
- **Quality/license:** the repo provides reproducible Arabic baselines and the author reports the adversarial version is often slightly clearer, but the multi-speaker model is marked in progress. Crucially, no LICENSE file or explicit checkpoint license exists at this revision; do not ship or commercially fine-tune it without written clarification.

### 5. MMS-TTS Arabic — eliminated

- **Sources/revision:** [Fairseq MMS at `1ef816f2`](https://github.com/facebookresearch/fairseq/tree/1ef816f2cd7b4a9aa7adf8bd5635a644834738f1/examples/mms); [MMS README](https://github.com/facebookresearch/fairseq/blob/1ef816f2cd7b4a9aa7adf8bd5635a644834738f1/examples/mms/README.md); [Arabic model card](https://huggingface.co/facebook/mms-tts-ara); [open fine-tuning question](https://github.com/facebookresearch/fairseq/issues/5608).
- The MMS TTS release offers generator archives and larger “full model” archives with discriminator/optimizer state, and its inference script now selects MPS. Nevertheless, its documented TTS workflow is inference through a separate VITS clone; it does not expose an official MMS continuation/fine-tuning command. Fairseq’s own installation page says training needs an NVIDIA GPU and NCCL. That fails the project’s core requirement even though Arabic coverage and checkpoint availability are real.

## Apple Silicon training policy for the selected primary

1. Pin the exact SILMA Hugging Face revision and F5-TTS 1.1.7 commit above; do not train against moving `main`.
2. Use the CLI, not Gradio, with trusted local paths. Keep `attn_backend=torch` and `bnb_optimizer=False`; do not install FlashAttention, bitsandbytes, Triton, TensorRT, DeepSpeed, or a CUDA PyTorch wheel.
3. First smoke run: one MPS device/process, FP32, batch 1, 3–8 second clips, `num_workers=0`, no sample logging, retain one checkpoint, and 10–50 optimizer steps. Set `PYTORCH_ENABLE_MPS_FALLBACK=1` for correctness discovery.
4. Compare those losses and one fixed validation utterance against a short CPU run. Abort MPS if there are NaNs, materially divergent loss, hangs, or excessive fallback churn.
5. If memory is high, enable the F5 config’s activation checkpointing, shorten/max-filter clips, and increase gradient accumulation. Do not raise the MPS high-watermark beyond safe defaults on a 32 GB machine.
6. Only after parity: try FP16 cautiously. Accelerate’s MPS path is single-device only; do not configure DDP/NCCL.
7. Keep at least 8–10 GB unified memory free for macOS and preprocessing. Estimated working sets are planning figures; capture actual peak allocator/RSS during the smoke run before choosing the production batch.

## Source-audit evidence

The following patterns were searched in the exact source revisions above: `.cuda(`, `torch.cuda`, `nccl`, `bitsandbytes`, `flash_attn`, `triton`, `xformers`, CUDA extensions, and `mps`.

- F5-TTS 1.1.7: `bitsandbytes` is platform-gated out on ARM64 Darwin; core configs default to `attn_backend: torch`; optional FlashAttention is guarded. CUDA-heavy Triton/TensorRT code is isolated under `runtime/triton_trtllm`. Core `Trainer` delegates placement to Accelerate.
- SILMA source: optional FlashAttention definitions exist but the model config uses PyTorch attention; CUDA branches are primarily device selection/cache cleanup and do not form a training implementation (training is upstream F5).
- Piper: one unreferenced `to_gpu()` helper hardcodes CUDA; the active Lightning model is device-generic. No CUDA build or optional NVIDIA package is required.
- `tts-arabic-pytorch`: multiple concrete hard CUDA assumptions are present in preprocessing and adversarial training; standard training is CUDA-or-CPU only and requires editing to select MPS.
- XTTS: numerous CUDA assumptions exist in utilities/distributed paths; MPS defects are independently recorded in the upstream issue tracker.
- MMS/Fairseq: inference explicitly supports MPS, while the framework README says training requires NVIDIA GPU/NCCL and the MMS TTS docs do not provide fine-tuning.

## Go/no-go criteria

Proceed with SILMA only if the pinned dependencies install without a CUDA wheel, a 10–50-step MPS smoke run completes within the safe memory envelope, CPU/MPS loss is numerically sane, and fixed Arabic validation clips retain intelligibility/voice identity. If any of those fail after a narrow portability patch, switch to Piper rather than investing in XTTS/MMS porting. Before distribution, separately verify target-speaker consent, source-audio rights, and every pretrained checkpoint/data license; model-code licensing alone is insufficient.
